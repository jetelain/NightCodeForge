## 1. Context & Motivation

Analysis of the November 25 `v1-smoke` benchmark runs (`v1-smoke-Flint-latest-20261125-105706` and `v1-smoke-Qwen3.8-27B-latest-20261125-105720` on `feat/bench @ db1d3d7`, both scoring `14/28` / `50.0%`) revealed five remaining infrastructure, toolchain-discovery, grading, and prompt-hygiene bugs. Notably, several of these surfaced *because* Steps 11.58â€“11.61 fixed earlier blockers (most importantly, Step 11.61's manifest overlay activating `python:3.9`/`python:3.11` and `mocha-junit-reporter` on previously stale local datasets):

1. **Host `/usr/lib/x86_64-linux-gnu` Bind-Mount Breaks OpenSSL in Custom Python Images (`pallets__flask-5014`, `psf__requests-1921`, `ncf-cr-py-001` â€” 6 false negatives):**
   - Step 11.61's manifest overlay caused `python:3.9` and `python:3.11` (configured in Steps 11.58 and 11.60) to execute for the first time.
   - Step 11.60 assumed non-managed custom images were ABI-compatible with host-mounted shared libraries. However, `HostSdkDiscoveryService` discovers host WSL Ubuntu `/usr/lib/x86_64-linux-gnu` (OpenSSL 3.0, max symbol `OPENSSL_3.0.9`) and `ContainerEnvironmentFactory` sets `MountHostSdks = true` unconditionally, causing `ContainerMountAndDriftBuilder` to bind-mount host `/usr/lib/x86_64-linux-gnu` directly over Debian Trixie `python:3.9`/`python:3.11`'s `/usr/lib/x86_64-linux-gnu` (`/lib/x86_64-linux-gnu`, OpenSSL 3.5 / `OPENSSL_3.3.0+`).
   - Consequently, both agent sandboxes and verification containers fail with `ImportError: /lib/x86_64-linux-gnu/libcrypto.so.3: version 'OPENSSL_3.3.0' not found` whenever Python imports `_ssl` or runs `pip`â€”failing all 6 Python runs despite both models producing valid fixes on all 3 tasks.
2. **Distro-Packaged `rustup` (`/usr/bin/rustup` + `~/.rustup/toolchains/...`) Rejected by Pre-Flight Validation (`burntsushi__ripgrep-2576`, `ncf-cr-rust-001` â€” 4 errors):**
   - Step 11.60 added host-mounted Rust support and pre-flight validation assuming `sh.rustup.rs`-style installs (`~/.cargo/bin/{cargo,rustc}` + `~/.rustup`).
   - On Ubuntu WSL where `rustup` is installed via `apt`, `/usr/bin/cargo` and `/usr/bin/rustc` are symlinks to `/usr/bin/rustup` (and `~/.cargo/bin` does not exist), while the real toolchain binaries live inside the already-mountable `~/.rustup/toolchains/<toolchain>/bin/{cargo,rustc}`.
   - Because `HostSdkDiscoveryService` resolves `which cargo` -> `/usr/bin/cargo` (`/usr/bin` is excluded from container mounts) without resolving the active toolchain binaries via `rustup which` or `~/.rustup/toolchains/*/bin`, `BenchmarkToolchainPreflightValidator` rejects both Rust instances in 0s even though `rustup` and `stable-x86_64-unknown-linux-gnu` are installed in WSL.
3. **Isolated `mocha-junit-reporter` Install Pulls ESM `mocha@12` on Node 18 (`axios__axios-5892` â€” 2 false negatives):**
   - Step 11.58 switched `axios__axios-5892` to `JUnitXml` + `mocha-junit-reporter`, and Step 11.61's manifest overlay activated it for the first time.
   - `BenchmarkTestCommandResolver` provisions the isolated reporter via `npm install --prefix /tmp/ncf-mocha-junit ... mocha-junit-reporter` without suppressing peer dependencies. `npm` 9 auto-installs `mocha@12.0.3` (ESM-only, requiring Node `>=20.19`) as a peer dependency inside `/tmp/ncf-mocha-junit/node_modules/mocha`, so `mocha-junit-reporter`'s own `require('mocha')` resolves that sibling ESM-only `mocha@12` instead of `/workspace/node_modules/mocha` on Node `v18.19.1` and crashes with `Error [ERR_REQUIRE_ESM]` before any test executesâ€”even though both models produced valid patches.
4. **Review Corpus & Expected-Finding Anchor False Negatives (`ncf-cr-csharp-008`, `ncf-tr-rust-002` â€” 2 false negatives on Qwen3.8-27B):**
   - **`ncf-cr-csharp-008`:** Step 11.61 allowed omitting `file_path` only when `symbol_or_line_hint` (`DecorrelatedJitterBackoffV2`) matched verbatim alongside majority independent keywords. Qwen delivered an empirically verified `RequestChanges` review matching 4/5 independent keywords (`IsNaN`, `Math.Abs`, `OverflowException`, `test`) and naming `RetryHelper` and `RetryHelperTests.cs`, yet failed because neither `RetryHelper.cs` nor the private method name `DecorrelatedJitterBackoffV2` appeared verbatim in `request_changes`.
   - **`ncf-tr-rust-002`:** Qwen explicitly cited `tokio-util/src/time/delay_queue.rs:579` in its assistant message immediately preceding `ask(...)`, but `CrucibleAgentHarness` replaces `Summary` with the static placeholder `"Crucible paused awaiting human clarification"` on `WaitingForHuman`, and `VerifyTaskReviewAsync` only evaluates `UpdatedTaskMarkdown`, `q.Prompt`, `q.Rationale`, and `Summary` (omitting both the assistant's pre-`ask` text and `q.OptionsJson`).
5. **Verifier Reporter Flags Leaking into Agent `<execution_guidelines>` & Docusaurus Build Command (`facebook__docusaurus-9897` and multi-stack runs):**
   - Step 11.61's `--ignore-scripts` guidance resolved `sharp` postinstall failures (`yarn install --frozen-lockfile --ignore-scripts` succeeded in ~245s), but `BenchmarkTestCommandResolver.ResolveAgentTestCommand` still returns verifier `CustomTestCommand` verbatimâ€”leaking verifier-only flags (`--reporters=jest-junit`, `--logger trx --results-directory /workspace/.ncf-bench-results`, `--reporter=junit --outputFile=...`) into agent `<execution_guidelines>` even when verifier-only reporters are absent in the agent container.
   - In addition, Node monorepos such as `facebook/docusaurus` receive `npm run build` (which executes `yarn build:packages && yarn build:website`) rather than `yarn build:packages`, causing agents to spend excessive time building documentation websites instead of compiling packages for Jest.

## 2. Required Behaviors & Constraints

### 2.1 Custom Container Image Shared-Library ABI Isolation
- Non-managed custom container images (`!IsManagedBaseImage(options.ContainerImage)`, such as `python:3.9`, `python:3.11`, or custom language base images) MUST exclude host OS multiarch shared-library directories (`/usr/lib/x86_64-linux-gnu`, `/usr/lib/aarch64-linux-gnu`, and equivalent `/usr/lib/*-linux-gnu*` / `/lib/*-linux-gnu*` multiarch library pathsâ€”whether discovered by `HostSdkDiscoveryService` or provided via `ContainerExecutorOptions.DefaultSdkMountPaths`) from container bind mounts so the container's own system shared libraries are never shadowed.
- `ContainerMountAndDriftBuilder` mount drift detection (`EvaluateMountDrift`) MUST flag any existing non-managed custom-image container that still carries a host OS shared-library mount as drifted (`expected absent`) so stale pre-fix containers are recreated rather than silently reused.
- Managed base images (`ncf-agent-base*` / `nightcodeforge-agent*`) MUST preserve existing host SDK and shared-library mount behavior, and non-managed custom images MUST retain non-ABI mounts (workspace, caches, `/etc/ssl/certs`, etc.).
- Containers using `python:3.9` and `python:3.11` MUST retain working stdlib `_ssl` and HTTPS `pip` functionality during both agent execution and benchmark verification without symbol-version conflicts (`OPENSSL_3.3.0`).

### 2.2 Distro-Packaged `rustup` Toolchain Discovery & Container `PATH` Wiring
- Preserve existing `sh.rustup.rs` (`~/.cargo/bin` + `~/.rustup`) discovery and proxy handling when `cargo` / `rustc` already resolve to a mountable directory.
- When `which cargo` / `which rustc` resolves to an excluded system directory (such as `/usr/bin/cargo` -> `/usr/bin/rustup` on `apt`-installed `rustup` where `~/.cargo/bin` does not exist), `HostSdkDiscoveryService` MUST resolve the active rustup-managed `cargo` and `rustc` binaries inside the mountable `$RUSTUP_HOME/toolchains/<active>/bin` directory (e.g., via `rustup which`, failing safely without breaking discovery when `rustup` has no configured default toolchain).
- Both `ContainerMountAndDriftBuilder` (`BuildDockerRunArgs` / `ComputePathEnvironmentVariable`, supplied via `ContainerEnvironmentFactory`) AND `PersistentContainerShellSession` (environment preamble) MUST expose the resolved `$RUSTUP_HOME/toolchains/<active>/bin` directory on the container `PATH` alongside `RUSTUP_HOME` and writable `CARGO_HOME=/cache/cargo`, without bind-mounting `/usr/bin` and without creating redundant or conflicting nested bind mounts under an already-mounted `$RUSTUP_HOME`.
- `BenchmarkToolchainPreflightValidator` MUST accept mountable `$RUSTUP_HOME/toolchains/.../bin/{cargo,rustc}` toolchains alongside `~/.cargo/bin` + `~/.rustup`, while continuing to fail fast with an actionable diagnostic both when only non-rustup system `/usr/bin/{cargo,rustc}` binaries exist and when `rustup` is installed without any configured/installed active toolchain.

### 2.3 Peer-Safe Isolated Node Reporter Provisioning
- Isolated Node test-reporter installation (`mocha-junit-reporter`, `jest-junit`) in `BenchmarkTestCommandResolver` MUST suppress peer dependency installation (e.g., via `--legacy-peer-deps` / `--omit=peer`) so conflicting test-runner packages (such as ESM-only `mocha@12` on Node 18) are never pulled into `/tmp/ncf-mocha-junit` or `/tmp/ncf-jest-junit`.
- Because Node resolves `require('mocha')` / `require('jest')` from an isolated prefix under `/tmp/ncf-*-junit/node_modules/*` by walking `/tmp` up to `/` and then checking `NODE_PATH` (never automatically checking `/workspace/node_modules`), `NODE_PATH` MUST include the workspace's `node_modules` (e.g., `"$PWD/node_modules"` alongside/ahead of `{prefix}/node_modules`) so the isolated reporter resolves peer `require()` calls cleanly against the repository's installed runner (`mocha` / `jest`) rather than failing with `Cannot find module 'mocha'` and so `axios__axios-5892` and equivalent Node suites emit valid JUnit XML.
- Isolated reporter provisioning MUST guard against pre-existing isolated prefixes (e.g., on persistent `/tmp` mounts) that already contain shadowed runner directories (`mocha` / `jest`) from prior runsâ€”by detecting/pruning shadowed runner packages or re-provisioning cleanly rather than blindly skipping installation when `{prefix}/node_modules/<reporter>` exists.

### 2.4 Review Corpus Preservation on `WaitingForHuman` & Grounded Finding Matching
- When `CrucibleAgentHarness` pauses with `AgentRunStatus.WaitingForHuman` (via `ask`), it MUST flush/capture visible pre-`ask` assistant analysis text (covering both buffered in-flight text in the `ask` turn and visible assistant text from earlier turns of the run, excluding hidden reasoning/thinking traces) and preserve it on `AgentRunResult` (falling back to a default placeholder summary only when no visible assistant text was emitted).
- Propagate this preserved assistant text through `CrucibleBenchmarkRunner` -> `BenchmarkAgentOutcome` -> `VerifyTaskReviewAsync` (and `BenchmarkLlmJudge` task-review prompt) alongside `UpdatedTaskMarkdown`, `Question.Prompt`, `Question.Rationale`, and option text extracted from `Question.OptionsJson` (supporting serialized JSON string/object arrays with raw-string fallback when non-JSON).
- Refine `BenchmarkVerifier.EvaluateExpectedFindings` while preserving existing Step 11.61 guarantees:
  - When a finding specifies `file_path`, `symbol_or_line_hint`, and `keywords`, allow strong independent keyword coverage (majority of $\ge 2$ non-overlapping independent keywords) to satisfy the finding when corroborated by **either** exact `symbol_or_line_hint` match **or** `file_path` / non-trivial identifier-bounded file-stem match (e.g., whole-word/identifier match on `RetryHelper` for `src/Polly.Core/Retry/RetryHelper.cs`, with a minimum length/specificity guard so short or generic stems such as `Log` or `http` cannot match unrelated substrings like `"catalog"` or `"https"`).
  - Continue rejecting ungrounded generic keyword matches (e.g., no file/stem/symbol match, or only a single generic keyword such as `"test"`), and preserve strict `file_path` grounding requirements for findings without `symbol_or_line_hint` (such as `TaskReview` findings).

### 2.5 Agent `<execution_guidelines>` Command Hygiene & Monorepo Package Build Detection
- `BenchmarkTestCommandResolver.ResolveAgentTestCommand` MUST strip verifier-only reporting/output flags and environment variable prefixes when deriving the interactive agent test command from `CustomTestCommand`:
  - `.NET`: `--logger` / `-l` (e.g., `--logger trx`, `--logger:trx`) and `--results-directory` (with `=` or space-separated argument, keeping `-r` / `--runtime` intact).
  - `Jest`: `JEST_JUNIT_OUTPUT_DIR=...`, `JEST_JUNIT_OUTPUT_NAME=...`, and `--reporters=jest-junit` / `--reporters jest-junit` (preserving `--ci` and non-verifier flags).
  - `Mocha`: `MOCHA_FILE=...` and `--reporter` / `-R` targeting `mocha-junit-reporter`, plus removing any now-empty trailing `--` separator (e.g., `npm run test:mocha -- --reporter mocha-junit-reporter` -> `npm run test:mocha`) while preserving `--` when remaining flags follow it.
  - `Vitest`: `--reporter=junit` / `--reporter junit` and `--outputFile=...` / `--outputFile ...` (preserving `-c vitest.unit.config.ts`).
  - `Pytest`: `--junitxml=...` / `--junitxml ...` / `--junit-xml=...` / `--junit-xml ...`.
- `BenchmarkTestCommandResolver.ResolveTestCommand` (benchmark verification execution) MUST remain unchanged and continue supplying all structured reporting flags, and `.NET` target discovery (`DiscoverDotNetTargets`) MUST still apply cleanly to stripped `dotnet test` commands.
- For Node/TypeScript monorepos whose root `package.json` defines a package-only build script (such as `build:packages`) alongside a full documentation/site `build` script, `BenchmarkStagePolicyResolver.BuildProjectConfig` MUST deterministically select the package-only build command using the repository's lockfile package manager (`pnpm run build:packages` for `pnpm-lock.yaml`, `yarn build:packages` for `yarn.lock`, `npm run build:packages` otherwise) in `<execution_guidelines>`, falling back cleanly to `CodeStackPresets.Node.BuildCommand` when `package.json` is absent, malformed, or lacks a package-only build script.
